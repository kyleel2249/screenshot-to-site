- ✅ RBAC with 8 roles; sensitive actions (refund, export, staff, settings) require recent re-authentication (`src/server/rbac.ts`)
- ✅ Storage boundary + in-memory reference DB (`src/server/db.ts`); SQL adapter must wrap the same atomic blocks in transactions
- ✅ Admin catalog service: create/validate products, single + bulk all-or-nothing status changes, pre-order explicitly enabled, price/sale validation, stock adjustment (never below reserved, reason + actor audited), publish/unpublish/archive, category admin (`services/catalog-admin.ts`)

- ✅ Order service: idempotent placement, server-side pricing, atomic stock/pre-order reservation, 30-min reservation expiry, verified-payment commit (no double deduction), mismatch → review, staff cannot manually confirm payment, IDOR-safe customer reads, privacy-safe tracking via secret, cancellation, refunds in order currency (`services/orders.ts`)

- ✅ Customer account service: profile (email/credentials not self-editable), addresses with strict ownership + default handling, wishlist, consent records, self-service data export, account deletion = anonymisation (orders retained without identity), staff customer view audited with no credentials (`services/account.ts`)

- ✅ HTTP API (Web `Request→Response`): CSRF via same-origin check, HttpOnly/Secure/SameSite=Strict cookies, rate limits, signature-verified payment webhook, customer/order/account routes with IDOR safety, secret-path admin API (404 for probes), dashboard changes visible on the public catalogue immediately, refunds/exports require step-up re-auth, errors never leak internals (`src/server/api.ts`, 12 end-to-end tests)

- 🟢 Wholesale quotes: public request form → reference + one-time access code → staff prices it (never automatic; revised quotes allowed until accepted) → requester accepts/declines on a status page; quotes expire; unknown ref and wrong code look identical (tested). - 🟢 Email: templates (verify email, owner verify, password reset, staff invite) + Resend HTTPS adapter in `src/server/mailer.ts`, wired through `deps.mail` when `EMAIL_API_KEY` and `EMAIL_FROM` are set; failures are logged without tokens and never break the request (tested with an injected fetch; never sent for real — no key). Notices (`deps.notify`): order received, quote ready, support reply — reference/subject only, never tokens or message bodies; internal notes and duplicate checkouts send nothing (tested)
- 🟢 Staff two-step verification (TOTP, RFC 6238 vectors pass; 8 hashed one-time recovery codes): a staff session is unusable (roles hidden, every admin route 403) until a code is proven; first sign-in forces setup; codes can't be replayed; 5 wrong codes in a row end the session (persisted, not just per-server rate limiting); owner can reset a colleague's second factor. Known limit: the TOTP secret is stored unencrypted in the database row (needed to verify codes) — protect database access; encrypting it at rest is a worthwhile hardening step. If the OWNER loses their phone and recovery codes there is no self-service path: an operator must clear the `mfa` field on the owner row in D1
- 🟢 Editable content pages (about, FAQ, shipping, returns, pre-order, privacy, terms): shipped defaults + owner edits, plain text only (no HTML injection path), public `GET /api/pages/:slug`, dashboard Content tab.
