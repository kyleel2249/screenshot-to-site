## Verified
- ✅ Money in integer minor units; GHS / USD / dual display; documented exchange rate required for any conversion (`src/lib/domain/money.ts`)
- ✅ Full 15-group category taxonomy (A–O) with admin operations: add/rename/hide/reorder (`categories.ts`)
- ✅ 12-status product system; one purchasability rule; promo labels honest (no fake scarcity/sale), scheduled expiry (`status.ts`)
- ✅ Server-style cart pricing: stock, preorder allocation, sale windows, discount rules, shipping zones, free-shipping (`commerce.ts`)
- ✅ Order state machine; idempotent payment-event handling; amount/currency mismatch → manual review, never "paid"
- ✅ PBKDF2 password hashing, signed expiring sessions, rate limiter, CSV formula-injection guard (`security/crypto.ts`)
- ✅ One-time admin enrolment (hash-compared bootstrap reference, closes permanently, rate-limited, audit never logs secrets), non-obvious portal path rule, single-use expiring password reset that revokes sessions (`security/enrolment.ts`)
- ✅ Relational schema (D1/SQLite) with constraints enforced: no negative stock, valid statuses, unique webhook events, append-only audit log, one-row admin setup (`db/migrations/0001_init.sql`)

- ✅ RBAC with 8 roles; sensitive actions (refund, export, staff, settings) require recent re-authentication (`src/server/rbac.ts`)
- ✅ Storage boundary + in-memory reference DB (`src/server/db.ts`); SQL adapter must wrap the same atomic blocks in transactions
- ✅ Admin catalog service: create/validate products, single + bulk all-or-nothing status changes, pre-order explicitly enabled, price/sale validation, stock adjustment (never below reserved, reason + actor audited), publish/unpublish/archive, category admin (`services/catalog-admin.ts`)
- ✅ Auth service: customer registration (no enumeration, marketing never pre-ticked), email verification, login with generic errors + lockout, signed revocable sessions, single-use password reset that revokes sessions, staff-initiated reset without exposing secrets, owner enrolment adapter (`services/auth.ts`)
- ✅ Order service: idempotent placement, server-side pricing, atomic stock/pre-order reservation, 30-min reservation expiry, verified-payment commit (no double deduction), mismatch → review, staff cannot manually confirm payment, IDOR-safe customer reads, privacy-safe tracking via secret, cancellation, refunds in order currency (`services/orders.ts`)

- ✅ Customer account service: profile (email/credentials not self-editable), addresses with strict ownership + default handling, wishlist, consent records, self-service data export, account deletion = anonymisation (orders retained without identity), staff customer view audited with no credentials (`services/account.ts`)
- ✅ Discount + shipping-zone admin with validation, permissions, audit; redemptions counted only on verified payment (`services/promotions.ts`)
- ✅ Support tickets: customers see only own tickets without internal notes (`services/support.ts`)
- ✅ Privacy-first analytics: consent-gated, daily-rotating pseudonyms, PII rejected, purchases only from verified orders, per-currency net revenue, small-group suppression, permissioned/audited/formula-safe CSV export (`services/analytics.ts`)
- ✅ Payment webhook HMAC verification (fails closed, optional replay window) (`lib/payments/webhook.ts`)
- ✅ Strict CSP (nonce scripts, no framing) + security headers + no-store helper (`lib/security/headers.ts`)
- ✅ Sitemap/robots generation: published public URLs only, XML-escaped (`lib/seo/sitemap.ts`)

- ✅ Transactional persistence: serialisation, compare-and-swap commit with retry, SQLite/D1 adapter, memory adapter. **10 concurrent buyers of the last unit → exactly one succeeds**, same-key double-submits create one order (both adapters) (`src/server/persistence/`)
- ✅ HTTP API (Web `Request→Response`): CSRF via same-origin check, HttpOnly/Secure/SameSite=Strict cookies, rate limits, signature-verified payment webhook, customer/order/account routes with IDOR safety, secret-path admin API (404 for probes), dashboard changes visible on the public catalogue immediately, refunds/exports require step-up re-auth, errors never leak internals (`src/server/api.ts`, 12 end-to-end tests)
- ✅ Docs: `docs/API.md`, `docs/DEPLOYMENT.md`
